# front-dancehall

Frontend каталога Dancehall Steps на React, TypeScript и Vite. Контракт API —
[`openapi.yml`](openapi.yml).

## Требования

- Node.js 24 LTS
- npm 11

## Локальный запуск

```bash
npm ci
npm run dev
```

Все запросы идут через `/api/v1`. Vite проксирует `/api/*` в backend на
`http://127.0.0.1:8080`, сохраняя полный путь, включая `/api`.
Операции Auth и Users пока описаны только контрактом: тесты используют HTTP-моки,
а приложение при недоступном API показывает ошибку с возможностью повторить запрос.

Каталог доступен по `/`, карточка степа — по `/steps/:slug`. Поиск и фильтры
сохраняются в URL; прямые ссылки и кнопки назад/вперёд работают через History API.

## Регистрация и сессия

Экраны: `/register`, `/verify-email`, `/login`, `/forgot-password`,
`/reset-password`, `/profile`. Каталог и страницы степов доступны без входа.
При запуске проверяется `GET /api/v1/users/me`; `401` включает гостевой режим,
при сетевой ошибке доступна повторная проверка. Профиль проверяется заново при
переходе на него, возвращении фокуса окна и нажатии «Обновить профиль».

Браузер управляет cookie сессии. Профиль, CSRF и токены ссылок хранятся только
в памяти; пароли и токены не записываются в Web Storage. Перед первым POST
получается `GET /auth/csrf`, затем передаётся `X-CSRF-TOKEN` вместе с cookie.
После входа и выхода CSRF получается заново. При `403 CSRF_INVALID` клиент
обновляет токен и повторяет POST ровно один раз. Если обновление CSRF после уже
успешного входа или выхода недоступно, следующий POST снова запросит токен.

**Для согласования с бэкендом:** письма должны ссылаться на frontend origin
с URL следующего вида (токен необходимо кодировать как значение URL):

```text
/verify-email#token=...
/reset-password#token=...
```

Страница считывает токен из fragment и удаляет fragment через History API с
заменой текущей записи. Подтверждение email выполняется только по кнопке;
новый пароль отправляется только после отправки формы. Query-параметр `token`
не используется. Ссылки действуют 24 часа для подтверждения email и 30 минут
для восстановления пароля согласно контракту.

Ответ `202` сопровождается нейтральным предложением проверить почту, без
подтверждения наличия аккаунта или доставки. Повторный запрос письма блокируется
на 60 секунд; при `429` учитывается `Retry-After` (для писем — не менее 60 секунд).

## Проверки

```bash
npm run check
```

Команда запускает lint, проверку форматирования, TypeScript, Vitest, production
build и HTTP smoke-тест статических маршрутов. Отдельно тесты запускаются через
`npm test`.

## Production

GitHub Actions упаковывает `dist` в проверяемый статический архив. После push в
`main` архив передаётся на VPS и атомарно становится активной версией frontend.

До первичной настройки VPS деплой отключается repository variable
`PRODUCTION_DEPLOY_ENABLED=false`. После установки серверного deploy script и
добавления environment secrets `DEPLOY_SSH_KEY` и `DEPLOY_KNOWN_HOSTS` переменную
нужно переключить в `true`; последующие push в `main` будут деплоиться автоматически.

Nginx обслуживает frontend по `/`, а `/api/*` проксирует в backend. Для прямых
ссылок на `/steps/:slug` Nginx должен отдавать `index.html` через SPA fallback
(`try_files $uri $uri/ /index.html`) только для frontend-маршрутов; API нельзя
перехватывать этим fallback.
